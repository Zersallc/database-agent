# A3 engineering assessment

Question: does the current semantic routing approach reliably select the correct tool and source?

Basis: the nine result files of 2026-09-21 (commit 46ee7ff, model `syslab-default`), read through the existing analysis (`a3-analysis.md`, generated by `evals/analyze.ts`). Every figure here was recomputed from the raw result JSON by a separate script, and all agree. Nothing was tuned, re-run, committed, pushed or deployed. The generated report keeps its `Assessment: TBD` lines; this document is the review of it.

## Answer

**No, not reliably.** Routing is dependable for some question shapes and unreliable for others, and the failures repeat: 17 of 24 media cases have the same pass count in both passes and the rest differ by at most three runs. The pattern is question-specific rather than a property of the workspace. The same workspace shape gets a search 10/10 for one question and 0/10 for another.

Reliable, in both passes: SQL-only questions with a library attached (5 of 6 questions), a specific document question with a database attached, cross-source when the document half is phrased as what a contract says, "checked the other source first" cases, unauthorized requests, and live retrieval of specific questions (30/30).

Unreliable, in both passes: whether the model calls `search_documents` at all for many document questions (it answers without a tool), questions that need two sources (SQL only, or one library of two), and the rule to ask first when the source is materially ambiguous (0 of 40 runs asked).

Provenance and rendering are a separate result and are clean (section 7). A clean provenance result does not offset the routing findings, and the routing findings say nothing against provenance.

## 3. What the controls establish

Each control is one case with one source removed, run once (10 runs), read against both passes. Fisher p is descriptive. The two passes of one case differ by up to three runs, so a one-to-two-run gap is not a difference.

**A confound in the no-database control.** The application builds the prompt from the sources present. With exactly one source left (one library, no database) it leaves out the "Choosing a source" section and swaps the connection intro for "No database is attached... Answer from the document libraries above" (`lib/agent/prompt.ts`, `buildSystemPrompt`). So that control removes the database, the routing-policy section and the intro wording together, and cannot say which of the three moved the result. The other two controls change only the sources (the routing section stays in the relevant-libraries control; the no-library control gives the pure database-only prompt).

| Case | Pass 1 / 2 | Control | Reading |
|---|---|---|---|
| **No database** | | | |

What this establishes:

1. **Changing the sources changes what the model does for particular questions, in both directions.** No single workspace explanation covers the results: not "a database distracts from the library", not "other libraries distract", not "a library-only workspace under-searches". Each holds for some questions and fails for others.
2. **Three failures are not explained by workspace composition**: leave-policy and two-relevant (unchanged with only the relevant libraries, same prompt sections), and `media-only-no-database` (0/10 in both passes, while three other questions searched 10/10 with the identical no-database prompt). They belong to the question, not the sources.
3. **Where a control did restore 10/10** (paraphrase, audit-findings, revenue-by-region), the extra sources had suppressed the right tool call. That is a model decision and not a grader or fixture effect, because grading and fixtures are identical in the control. For audit-findings and revenue-by-region the change is source count only. For paraphrase it is the confounded control above.
4. The vague-request pattern is consistent across four measurements: with a database and the routing section, 20/20; without them, 0/10, 0/10, 0/10 and 1/10 (vague-library-only twice, live once, the control once). The application changes database presence and the routing section together, so this cannot be attributed to either.
5. The controls do not say why. They rule out workspace composition as the whole story and identify one variable (the routing section, present only with two or more sources) that moves with the results and is not separated from database presence.

## 5. Against A0

- **Database-only did not regress.** The original eleven cases are 110/110 at A0, 110/110 in the rerun and 110/110 with a library attached (p 1.00; Wilson 97-100%), and the attached library was searched in 0 of 110 runs. `naming-multi-connection-ambiguous` is 10/10 in all three.
- **Cost of adding libraries** (agent only, the earlier report mixed in grading calls; ISS-08): input tokens per request 3,028 (A0), 3,180 (database only), 3,784 (library attached, +19% over database only); per run 7,680, 7,516, 9,632 (+28%). In the nine cases whose request structure is identical, the library sections add **612 to 632 input tokens per request**. In the four cases where A0 and the rerun made the same number of requests, the database-only prompt differs from A0 by 0.0 to -0.4 tokens per request.
- **Existing SQL behavior is equivalent in outcome, not identical in activity.** With a library attached, `naming-abbreviated-table` and `naming-decoy-table` make one extra request in every run (20/20), each recorded as a backstop retry. Database-only had none for them. Which backstop fired is not stored (the result keeps a boolean), so the reason is unknown; pass counts are unaffected. Separately, A0 made 279 agent requests against 260 in the rerun for the same cases and the same pass counts, which the data cannot explain.
- **What A0 cannot tell us**: it has no run-level detail, so no tools, sources, retries or provenance per run. It has none of the media families. Those are measured against the plan's conditions and not against A0. The original cases are at 100%, so they cannot show a regression smaller than a case's own strictness. The one SQL sensitivity found (revenue-by-region) is in a case A0 does not contain, established by the no-library control.

## 6. Repeatability of the two media passes

Same commit, model name, endpoint, suite, repeat, cases and order. 17 of 24 cases have the same pass count, 16 the same tool patterns, 17 the same primary cause. The nine that differ: paraphrase 6→3 (p 0.37), leave-policy 1→2, audit-findings 5→4, payment-terms 7→8, revenue-by-region 5→6, penalty-rate 10→9, uncovered-customer 10→9, and two with the same pass count but different tool patterns. Totals 144 and 141. Every difference of 1-3 runs is inside what ten draws of one prompt produce.

**This is not a controlled repeat.** Between the passes I made three evaluation-side changes (12:23-12:25 UTC; pass 1 ended 12:21, pass 2 began 12:25): E1, the provenance grader stopped demanding citations of files the run never retrieved; E2, one-primary-cause classification; E3, `--variant` support. E1 can only remove a failure. It flagged 10 pass-1 runs of `media-multi-two-relevant`, and all 10 also failed routing and the answer, so no pass count changes. E2 is applied when a result is read, identically to both, and E3 branches only when the flag is used (neither pass used it). So the pass counts are unaffected by the changes. The result files cannot show it: their recorded working-tree lists are identical although the changed files' contents are not.

Can be inferred: which cases are stable, and the size of ten-run sampling noise. Cannot be inferred: stability across days or model versions (the result records a model name and endpoint, not a version), or that the gateway load was the same (it is shared with the live site).

## 10. Demonstrated and unresolved

**Demonstrated.** The deterministic pieces work: authorization, provenance and its rendering, no rate-limit or infrastructure loss, no unnecessary searches in SQL-only work, and no change to the database-only prompt or the original cases' outcomes. Where the model does search, it picks the right library and retrieval works. When it routes right, its answer is right.

**Not demonstrated, and unreliable.** That the model calls the right tool for document questions, for questions needing two sources, and that it asks first when a source is materially ambiguous. Not fixed by removing sources.

**Unresolved.**
1. The mechanism of the no-tool failures. The wording echo is a lead only.
2. ISS-03, ISS-06, ISS-07 (the expectation and grader decisions) and the thresholds.
3. Whether the material-ambiguity fixtures make the ambiguity visible to the model.
4. Which backstop fires in the two library-attached SQL cases: the result stores whether a retry fired, not which.
5. What the model says when it makes no call in cases with no answer check (revenue-by-region, vague, ambiguity).
6. Stability over time, and transfer to real corpora beyond four live questions.

**Smallest architectural question.** Which variable actually moves search-triggering: database presence, the routing-policy section (present only with two or more sources), or the connection intro? The application changes all three together, and the no-database results (fewer searches on a vague request, more on two specific ones) are consistent with the routing section acting in both directions. That decides whether the failures are addressable in the prompt at all or need an application-level check for the one observable signature (an answer about documents, or a pointer to a library, made with no search in the run). The loop already does that for the SQL analogue ("Answered without running a query — retrying"), so the pattern exists. This is a question for you and not a recommended fix: the evidence gives the failure signature and one candidate variable, not a mechanism, so I would not tune the prompt yet.

**Next step.** By your rule (clean → A4, regression → fix and re-test with your approval), this is not clean, but no threshold exists to call it a regression formally. I would decide the three expectation items and the thresholds first (no runs needed), then, with your approval, run one small designed diagnostic on the no-tool questions: vary the routing section and the intro independently of the database, and separately require a tool call, to tell a decision failure from a capability failure. A4 (service and routes) does not depend on routing quality; A6 rollout does.
